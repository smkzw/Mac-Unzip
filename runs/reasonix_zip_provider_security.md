# Security Review: ZIP Provider Vertical Slice

**Reviewer:** Reasonix CLI `deepseek-pro` — high-risk C bridge, filesystem, and transaction review
**Scope:** ZIP provider vertical slice only — `ArchiveWorkbench/Packages/ArchiveKit/Sources/ArchiveProviders/`, `CMinizipBridge/`, `ArchiveSecurity/`, and their tests
**Date:** 2026-07-12
**Outcome:** **REVISE**

---

## Severity Triage

| Rank | ID | Title | Exploitability |
|------|----|-------|----------------|
| CRITICAL | C1 | CRC never verified after decompression | Corrupted ZIP delivers silent garbage |
| CRITICAL | C2 | Unbounded entry iteration in `allEntries()` | Malicious ZIP hangs process indefinitely |
| HIGH | H1 | `AWB_MZ_OPEN_ERROR` / `AWB_MZ_IO_ERROR` collapse into `.helperFailed` | Caller cannot distinguish file-not-found from disk-full |
| HIGH | H2 | Advertised-size fully trusted for budget pre-check and `reserveCapacity` | Zip bomb with forged small `uncompressed_size` bypasses budget gate |
| HIGH | H3 | Source-fingerprint recheck happens after all files written, not per-file | Window for undetected source mutation scales with file count |

## CRITICAL Findings

### C1 — No CRC Verification After Decompression (file-integrity)

**Files:** `Sources/CMinizipBridge/AWBMinizipBridge.c:157–166`, `Sources/ArchiveProviders/ZIPArchiveProvider.swift:150–192`

**Evidence:**

- `awb_mz_reader_read_current` wraps `mz_zip_reader_entry_read` and returns the byte count on success. It does **not** call any minizip CRC-check API (e.g., `mz_zip_reader_entry_get_crc` or `mz_zip_entry_crc_verify`).
- `ZIPBridgeReader.readEntry` at line 188–190 verifies only **byte count equality** against `expectedSize`:
  ```swift
  guard UInt64(data.count) == expectedSize else {
      throw ArchiveError.corruptedArchive
  }
  ```
- Minizip 3.x *may* verify CRC internally during `mz_zip_reader_entry_read`, depending on build-time flags (`MZ_ZIP_SIGNING`, `MZ_ZIP_CHECK_CRC`). The bridge does not configure or assert CRC checking — it trusts minizip's default, which is not guaranteed across versions or platforms.

**Exploit scenario:** A corrupted archive entry whose compressed data decompresses to the correct size but wrong content passes the size check. An attacker who can flip bits in a stored ZIP (without altering the central-directory size fields) delivers malformed content that the provider accepts silently.

**Smallest safe correction:**
1. After the read loop, call a minizip CRC-verification function (e.g., compare `mz_zip_reader_entry_get_crc(reader->handle)` against `file_info->crc`) and return `AWB_MZ_CRC_ERROR` on mismatch.
2. In `ZIPBridgeReader.readEntry`, map `AWB_MZ_CRC_ERROR` to `.corruptedArchive` (the mapper in `ZIPProviderErrorMapper` already does this). Add an explicit post-read CRC assert:
   ```swift
   // After close_current succeeds:
   guard crc == expectedCRC else { throw ArchiveError.corruptedArchive }
   ```

**Required regression test:** Construct a valid ZIP, flip one byte in the compressed data of one entry with a binary editor, verify `readEntry` throws `.corruptedArchive`, not just a size mismatch.

### C2 — Unbounded Entry Iteration Hangs on Corrupted ZIP (denial-of-service)

**Files:** `Sources/ArchiveProviders/ZIPArchiveProvider.swift:135–148`

**Evidence:**

```swift
func allEntries() throws -> [ZIPBridgeEntry] {
    guard let handle else { throw ArchiveError.helperFailed }
    var result: [ZIPBridgeEntry] = []
    var info = awb_mz_entry_info()
    var status = awb_mz_reader_first(handle, &info)
    while status == AWB_MZ_OK {
        result.append(try copy(info))
        status = awb_mz_reader_next(handle, &info)
    }
    guard status == AWB_MZ_END else {
        throw ZIPProviderErrorMapper.archiveError(for: status)
    }
    return result
}
```

- The loop has **no iteration cap**. A corrupted ZIP whose central directory forms a cycle or reports a very large entry count causes `awb_mz_reader_next` to keep returning `AWB_MZ_OK`.
- The `result` array grows without bound until the process is OOM-killed or the user force-quits. This is a **hang/DoS**, not a crash.

**Exploit scenario:** An attacker delivers a malformed ZIP with a cyclic or artificially inflated entry count. The app calls `open(url:)` and hangs on the main cooperative thread (actor), making the archive feature unresponsive.

**Smallest safe correction:** Cap the iteration to a reasonable upper bound (e.g., `1_000_000` entries, matching `ResourceBudget.extractionDefault.maxEntries`). If the loop exceeds this, throw `.corruptedArchive`:
```swift
let maxEntryCap: Int = 1_000_000
while status == AWB_MZ_OK {
    guard result.count < maxEntryCap else {
        throw ArchiveError.resourceLimit
    }
    result.append(try copy(info))
    status = awb_mz_reader_next(handle, &info)
}
```

**Required regression test:** Construct a ZIP with a forged central-directory entry count of `UINT16_MAX`. Verify `open(url:)` throws within a bounded time (< 1 second on a modern Mac).

## HIGH Findings

### H1 — Error-Code Collapse: `AWB_MZ_OPEN_ERROR` / `AWB_MZ_IO_ERROR` Become `.helperFailed` (caller ambiguity)

**Files:** `Sources/CMinizipBridge/AWBMinizipBridge.c:18–44`, `Sources/ArchiveProviders/ZIPProviderError.swift:5–18`

**Evidence:**

The C bridge defines eight distinct error codes:
```c
#define AWB_MZ_OPEN_ERROR -2
#define AWB_MZ_IO_ERROR   -7
```
The Swift mapper `ZIPProviderErrorMapper.archiveError(for:)` has a **default case** at line 16:
```swift
default:
    return .helperFailed
```
This catches `AWB_MZ_OPEN_ERROR` (file not found / permissions), `AWB_MZ_IO_ERROR` (disk full / read error during decompression), `AWB_MZ_OK` (should never reach error mapper), `AWB_MZ_END` (same), and `AWB_MZ_INVALID_ARGUMENT` (programming error).

**Impact:** The caller cannot distinguish "the ZIP file was deleted between listing and read" from "the disk is full during decompression" from "minizip hit an unknown internal error." Retry logic, user-facing messages, and fallback behavior all degrade.

**Smallest safe correction:** Add explicit cases:
```swift
case AWB_MZ_OPEN_ERROR:   return .helperFailed   // or a new .fileUnavailable
case AWB_MZ_IO_ERROR:     return .resourceLimit   // or a new .ioError
```
At minimum, map `AWB_MZ_IO_ERROR` to `.resourceLimit` (disk space is a resource issue) and keep `AWB_MZ_OPEN_ERROR` as `.helperFailed` with a documentation note.

**Additional C-side conflation:** `MZ_DATA_ERROR` (data corruption during read) is mapped to `AWB_MZ_FORMAT_ERROR` (line 30), which becomes `.corruptedArchive` in Swift. This is *mostly* correct, but `MZ_EXIST_ERROR` (file-already-exists) is also folded into this bucket — a condition that may arise during writer operations under a different semantic.

**Required regression test:** Test that `readEntry` on a ZIP whose backing file is `unlink()`'d during the read loop throws a distinguishable error (not just `.helperFailed`).

### H2 — Advertised-Size Trusted for Budget Pre-Check (zip bomb bypass)

**Files:** `Sources/ArchiveProviders/ZIPArchiveProvider.swift:90–96`, `Sources/ArchiveSecurity/ResourceBudget.swift:36–42`

**Evidence:**

`materializeEntry` performs a budget evaluation using **advertised** sizes:
```swift
let decision = budget.evaluate(ResourceEstimate(
    compressedBytes: snapshot.compressedSize,
    expandedBytes: snapshot.uncompressedSize,
    entries: 1,
    depth: 1
))
guard decision == .allow else { throw ArchiveError.resourceLimit }
let data = try readEntry(id: id, maximumBytes: budget.maxExpandedBytes)
```

A malicious ZIP can advertise `uncompressed_size = 100` (passes `maxExpandedBytes: 256MB` and `maxRatio: 50` checks) while the actual compressed payload decompresses to gigabytes. The budget gate **passes**, and the only protection is the runtime size cap in `readEntry` at line 176–179:
```swift
let nextSize = UInt64(data.count) + UInt64(count)
if nextSize > maximumBytes {
    readError = .resourceLimit
    break
}
```

**Impact:** The budget gate is decorative — it provides no real protection because every field it evaluates comes from untrusted archive metadata. The runtime cap in `readEntry` is the true defense. This creates a false sense of security if someone later adds a path that skips `readEntry` but trusts the budget decision.

**Smallest safe correction:** Either:
1. Document that `budget.evaluate` is an *optimistic pre-check* and the real enforcement is `maximumBytes` in `readEntry`; or
2. After reading the entry, assert `data.count <= budget.maxExpandedBytes` as a post-condition (redundant but self-documenting).

**No code change strictly required** as long as the runtime cap is the authoritative limit — but the naming is misleading.

**Required regression test:** Create a ZIP with a stored entry advertising `uncompressed_size = 1` but containing a deflate bomb that expands to 10× `maxExpandedBytes`. Verify it throws `.resourceLimit` from `readEntry`, confirming the runtime cap works.

### H3 — Source-Fingerprint Recheck After All Files Written (TOCTOU window)

**Files:** `Sources/ArchiveProviders/WindowsZIPProfile.swift:31–38`

**Evidence:**

```swift
for file in files {
    try writer.add(sourceURL: file.sourceURL, archivePath: file.archivePath)
}
for file in files {
    guard try file.fingerprint == SourceFingerprint(url: file.sourceURL) else {
        throw ArchiveError.sourceChanged
    }
}
```

The re-fingerprint loop runs **after** all files have been added. If file 1 changes during the write of file 2, file 1's old content is already in the staging ZIP. The TOCTOU window is **proportional to the number and size of files**, not just the per-file read time.

The fingerprint itself (`SourceFingerprint`) uses `fileResourceIdentifier` + `fileSize` + `contentModificationDate` — strong against replacement and size changes, but blind to same-size + same-mtime content swaps within the same second (microsecond granularity on APFS, but second granularity in the `Date` API).

**Smallest safe correction:** Re-fingerprint each file **immediately after** `writer.add(...)`:
```swift
for file in files {
    try writer.add(sourceURL: file.sourceURL, archivePath: file.archivePath)
    guard try file.fingerprint == SourceFingerprint(url: file.sourceURL) else {
        throw ArchiveError.sourceChanged
    }
}
```
This tightens the window to the single-file read time. For maximum protection, compute a content hash (SHA-256) of the source before writing and verify it against the bytes minizip actually read — but that requires minizip API changes.

**Required regression test:** In a test, modify a source file (same size, updated mtime) on a background queue while `createWindowsZIP` is writing a different large file. Verify the re-fingerprint catches the change. (This is inherently racy, so the test must be probabilistic or use file-coordination hooks.)

## MEDIUM Findings

### M1 — `reader->current` Dangling Pointer Across Entry Navigations

**Files:** `Sources/CMinizipBridge/AWBMinizipBridge.c:46–78, 67, 150–155`

**Evidence:**

```c
reader->current = file_info;   // line 67 — points into minizip internals
```

`file_info` is obtained from `mz_zip_reader_entry_get_info`. Minizip's documentation does not guarantee the pointer remains valid after the next `goto_first_entry` / `goto_next_entry` call. After `awb_mz_reader_close_current`, `reader->current` still holds the old pointer. If a future code path calls `awb_mz_reader_open_current` after navigation without an intervening `fill_info`, the NULL check at line 151 passes (pointer is non-NULL) and minizip is asked to open a stale entry.

In the **current** call chain, `fill_info` is always called by `first`/`next`/`goto` before `open_current`, so this is dormant. But the invariant is undocumented and fragile.

**Smallest safe correction:** Clear `reader->current` in `awb_mz_reader_close_current`:
```c
int32_t awb_mz_reader_close_current(awb_mz_reader *reader) {
    ...
    reader->current = NULL;  // add this
    return awb_mz_map_result(mz_zip_reader_entry_close(reader->handle));
}
```

**Required regression test:** Call `open_current` after `close_current` without an intervening `goto`/`first`/`next`. Verify it returns `AWB_MZ_INVALID_ARGUMENT`.

### M2 — Encrypted Entries Not Rejected Before Decompression Attempt

**Files:** `Sources/ArchiveProviders/ZIPArchiveProvider.swift:60–80`

**Evidence:**

```swift
guard !snapshot.isDirectory, !snapshot.isSymbolicLink else {
    throw ArchiveError.unsafePath
}
// ⬆ No check for snapshot.isEncrypted
```

An encrypted entry passes the directory/symlink guard and proceeds to `reader.readEntry()`. Minizip detects the encryption on `mz_zip_reader_entry_open` or `mz_zip_reader_entry_read` and returns an error (likely `MZ_PASSWORD_ERROR` or `MZ_CRYPT_ERROR`). The C bridge maps these to `AWB_MZ_PASSWORD_ERROR`, and the Swift mapper returns `.wrongPassword`.

The error message is misleading — the user never provided a password, so "wrong password" is confusing. The correct error should be `.passwordRequired` (which exists in `ArchiveError` at `ArchiveDomain/ArchiveError.swift:2`).

**Smallest safe correction:** Add an explicit guard in `readEntry`:
```swift
guard !snapshot.isEncrypted else {
    throw ArchiveError.passwordRequired
}
```

**Required regression test:** Create a password-protected ZIP entry. Verify `readEntry` throws `.passwordRequired`, not `.wrongPassword`.

### M3 — `ZIPBridgeWriter.deinit` Silently Discards Close Errors

**Files:** `Sources/ArchiveProviders/WindowsZIPProfile.swift:253–255`

**Evidence:**

```swift
deinit {
    if handle != nil { _ = awb_mz_writer_close(&handle) }
}
```

If `awb_mz_writer_close` fails (e.g., disk full during final central-directory write), the error is discarded. The caller (`finish()` at line 270–276) calls `awb_mz_writer_close(&handle)` explicitly and checks the result — but if `finish()` is **never called** (e.g., due to an early return or exception), the deinit runs and the error is lost.

This is a secondary path — the primary path (`finish()`) is correct. But if someone adds an early-exit code path that skips `finish()`, truncated ZIP files are silently accepted.

**Smallest safe correction:** Log the discarded error at minimum:
```swift
deinit {
    if handle != nil {
        let status = awb_mz_writer_close(&handle)
        if status != AWB_MZ_OK {
            assertionFailure("ZIPBridgeWriter deallocated without explicit finish; close returned \(status)")
        }
    }
}
```
Even better: make `finish()` the **only** way to close, and assert in deinit that `handle == nil`.

**No regression test required** for a deinit-only path (untestable), but a test verifying that `finish()` followed by deinit does not double-close is valuable.

### M4 — Directory Entries in ZIP Listing Bypass Path Validation (info disclosure)

**Files:** `Sources/ArchiveProviders/ZIPArchiveProvider.swift:27–33`

**Evidence:**

```swift
if !bridgeEntry.isDirectory {
    do {
        try ArchivePathPolicy().validate(displayPath)
    } catch {
        throw ArchiveError.unsafePath
    }
}
```

Directory entries skip `ArchivePathPolicy.validate`. A ZIP with a directory entry named `../../../etc/` produces an `ArchiveEntry` with `displayPath = "../../../etc/"` in the snapshot. This entry cannot be read or materialized (guarded by `!snapshot.isDirectory` in `readEntry`), but the path is **visible to the caller** in `ArchiveDocumentSnapshot.entries`.

**Impact:** Information disclosure — the caller sees traversal paths in the UI listing. This is low severity because (a) the entry cannot be acted on, and (b) the ZIP author already controls the entry names. But it violates the principle that validated paths are the only ones exposed.

**Smallest safe correction:** Either validate directory paths too (simplest), or strip directory entries that fail validation from the snapshot (more nuanced — loses legitimate directory structure).

```swift
if bridgeEntry.isDirectory {
    do {
        try ArchivePathPolicy().validate(displayPath)
    } catch {
        throw ArchiveError.unsafePath
    }
}
```

**Required regression test:** Open a ZIP containing a directory entry with `../` in its name. Verify `open()` throws `.unsafePath`.

## LOW — Missing Regression Tests

These are test gaps, not code defects. Each represents a scenario the current test suite does not cover.

| ID | Gap | Risk if untested |
|----|-----|-----------------|
| L1 | Zip bomb: forged `uncompressed_size=1` but large actual decompressed data | Silent bypass of budget gate (mitigated by runtime cap, but untested) |
| L2 | CRC corruption: flip one byte in compressed data, verify `.corruptedArchive` | CRC silently ignored if minizip CRC check is off |
| L3 | Source-change during write (TOCTOU): modify file while `createWindowsZIP` runs | Source fingerprint recheck never exercised in race condition |
| L4 | Reserved device names: `AUX`, `PRN`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, `CLOCK$` | Only `CON` is tested; other reserved names could slip through |
| L5 | Trailing space/dot in path component (e.g., `"readme. "`, `"readme."`) | Windows silently strips these — collision with legitimate files |
| L6 | Control characters in entry names (U+0000–U+001F, U+007F) | `ArchivePathPolicy` catches them, but ZIP listing test doesn't verify |
| L7 | Symlink entry inside ZIP (minizip `is_symlink` flag) | `readEntry` rejects, but no ZIP-with-symlink test fixture |
| L8 | Encrypted + non-encrypted mixed ZIP | `.wrongPassword` vs `.passwordRequired` behavior untested |
| L9 | Deep directory path (>100 components) in `SecureFileMaterializer` | FD exhaustion on descriptor-rooted traversal |
| L10 | Empty ZIP (zero entries) | `allEntries()` returns `[]` after `AWB_MZ_END` on first call — untested |

## Positive Findings (Correctly Hardened)

These patterns are **well-designed** and should be preserved:

1. **Descriptor-rooted materialization** (`SecureFileMaterializer.swift`): All operations use `*at` syscalls relative to `rootFD`, opened with `O_NOFOLLOW`. No path-based operations after the initial `open()`. The `published` flag pattern with `unlinkat` cleanup on failure is correct.

2. **Staging + atomic-link publication** (`WindowsZIPProfile.swift:41–42`): `createWindowsZIP` writes to a UUID-named staging file, fsyncs it, and atomically hard-links to the output. EEXIST is caught. On cleanup failure, the output is removed. No partial output files.

3. **Symlink rejection at multiple layers:**
   - C bridge: `mz_zip_writer_set_follow_links(0)` and `mz_zip_writer_set_store_links(0)`
   - Swift preflight: `SourceFingerprint` checks `isRegularFile` / `isSymbolicLink`
   - Directory enumeration: `files(under:)` rejects symlinks
   - Materializer: `O_NOFOLLOW` on every `open`/`openat`

4. **Runtime decompression-size cap** (`ZIPArchiveProvider.swift:176–179`): Even though the budget pre-check trusts advertised sizes, the read loop has a hard `maximumBytes` cap that stops decompression mid-stream.

5. **macOS metadata suppression** (`WindowsZIPProfile.swift:205–208`): `.DS_Store`, `__MACOSX`, and `._*` files are filtered from the Windows ZIP. Correct for cross-platform archives.

6. **NFC normalization** (`WindowsZIPProfile.swift:145`): `precomposedStringWithCanonicalMapping` ensures decomposed Unicode (common on macOS HFS+) is normalized to precomposed form for Windows compatibility.

7. **Case-insensitive collision with POSIX locale** (`WindowsZIPProfile.swift:158–159`): Uses `en_US_POSIX` for lowercasing, avoiding the Turkish 'I' problem.

---

## Verdict

**REVISE** — for this ZIP provider vertical slice only.

The descriptor-rooted materializer and atomic-link publication are well-designed. The critical gaps are:

1. **No CRC verification** — the provider trusts minizip defaults and byte-count equality, opening a silent data-corruption path.
2. **Unbounded entry iteration** — a trivial DoS vector in `allEntries()`.
3. **Error-code collapse** — callers cannot act on distinguishable failure modes.

These three alone warrant a revision pass before the slice is accepted. The remaining HIGH and MEDIUM items should be addressed in the same pass or explicitly documented as accepted risk.
