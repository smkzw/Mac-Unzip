## 路线逐项审判

### 审判方法论

对每个选项执行三条测试：
- **完整性测试**：是否满足用户批准的格式矩阵中的所有需求？
- **范围缩减测试**：是否通过悄悄放弃已批准需求来获得成功？
- **可实现性测试**：其核心主张在当前证据基础上是否可实现？

### 选项 C — 纯进程内库

**判决：已正确拒绝，但拒绝理由不够精确。**

Codex 审查指出选项 C "无法满足加密 7z 创建/提取或加密 RAR 提取"。证据审查更精确地揭示：

- libarchive 3.8.x 的 7z 写入器支持 Copy / Deflate / BZip2 / LZMA1 / LZMA2 / PPMd / Zstandard——但 **不包含任何 7z 加密写入路径**（engine_distribution_matrix.md 第 66 行确认）。
- libarchive 3.8.x **无法读取加密 RAR/7z 载荷**（第 67 行）。
- libarchive 的 RAR4/RAR5 读取器是独立、许可宽松的实现——这被 Codex 验证为正确——但它们不处理加密数据。
- minizip-ng 覆盖了 ZIP 加密（ZipCrypto + WinZip AES），但不涉及 RAR 或 7z。

因此选项 C 的失败点是精确且无可争议的：**它缺少加密 7z 写入、加密 7z 读取和加密 RAR 读取能力**——这三者都是用户已批准的格式矩阵中的硬性需求。这不是"不理想"，而是缺项。

**判决：拒绝，维持。理由已从"不足"升级为"缺项——已批准的三个加密格式路径完全缺失"。**

### 选项 B — 本地辅助程序中心

**判决：架构选项文档低估了其风险，需要更强有力的拒绝理由。**

选项 B 的关键主张是"最小的集成表面"和"最快的广泛覆盖路径"。但审查揭示了架构选项文档中未列出的更严重风险：

1. **每个常见操作的进程边界成本**：打开一个 ZIP、列出条目、预览单个文件、添加/删除条目——每个操作都通过 `7zz` 进程。对于包含 10,000 个条目的 ZIP，列表操作需要解析 7zz 的标准输出。对于包含数百个文件的批处理提取，每次提取都启动一个进程或使用复杂的一次性命令行。

2. **7zz 输出格式不是稳定 API**：`7zz` CLI 的输出格式可能在小版本间发生变化。架构文档承认"结构化错误映射"是必需的，但并未指定输出解析合同——它是一个不断移动的目标。

3. **7zz 并非每个格式的最佳引擎**：
   - 7zz 的 ZIP 实现是 7-Zip 项目的 ZIP 处理器，并非专门的 ZIP 库。在 PKWARE APPNOTE 合规性、ZIP64 过渡、中央目录恢复和传统编码方面，minizip-ng 专门为此构建且拥有更全面的测试覆盖（engine_distribution_matrix.md 记录的 244/244 测试）。
   - 对于 TAR/Zstandard 流式传输，libarchive 提供可链接的 C API 以实现结构化进度，而 7zz 仅提供进程输出。

4. **缺乏进程内优雅降级**：如果 `7zz` 缺少或损坏，选项 B 对所有非 DMG 格式完全失败。选项 A 至少保留了针对未加密 ZIP 的 minizip-ng 和针对未加密 TAR 系列与 ISO 的 libarchive——即 7zz 缺失时的部分功能。

5. **7zz + minizip-ng ZIP 输出的一致性**：如果稍后添加 minizip-ng 作为备用，选项 B 创建的 ZIP 归档可能表现出与选项 A 创建的 ZIP 不同的行为特征（不同的压缩率、不同的额外字段、不同的 ZIP64 阈值）。对依赖"相同归档产生逐字节相同输出"的用户，这种不一致会造成困扰。

**判决：拒绝，维持。其被接受为"有用的原型/回退路径"是正确的，但架构文档应更明确地指出它在生产环境中不可行——不仅仅是不如人意。建议在最终设计规范中将其降级为"仅用于集成测试的参考实现"。**

### 选项 A — 能力路由混合核心

**判决：暂定通过，附带重大条件。以下反证挑战是选项 A 在签署前必须解决的。**

选项 A 被推荐的原因是"使用每个格式最强的引擎满足全部范围"。但推荐基础中缺少几个关键设计要素，审查发现如下：

**已解决的主张**：
- minizip-ng 和 libarchive 的本地上游构建均通过零失败——这是可行性的有力证据（非推测）。
- 加密 ZIP (minizip-ng) + 加密 7z (7zz) + RAR 提取 (7zz) 的能力组合覆盖了已批准矩阵。没有遗漏的格式。
- 三个构建配置（Local/Direct/OpenSource）正确分离了打包问题，同时保持领域模型不变。

**未解决的主张——需要在签署前解决**：

1. **多引擎 ZIP 读取路由未指定**：minizip-ng 和 libarchive 和 7zz 都可以读取 ZIP。如果 minizip-ng 遇到无法处理的 ZIP 变体（例如旧版 Deflate64 或非标准额外字段），会回退到 libarchive 吗？还是回退到 7zz？回退策略可能导致不同的行为特征——一个引擎可能忽略某些额外字段而另一个引擎尊重它们。路由必须是确定性的且行为可重现的。**架构选项文档缺少引擎选择算法。**

2. **ZIP 写入跨引擎一致性**：仅 minizip-ng 写入 ZIP。但如果 7zz 用于提取加密 ZIP（因为它是唯一能处理某些边缘情况的引擎），则读取路径可能与写入路径不一致。用户通过 7zz 读取的 ZIP 再通过 minizip-ng（事务重建）保存，可能导致细微的元数据变化。**未指定读取器/写入器的往返一致性保证。**

3. **libarchive `archive_write_disk_header()` 的 umask 问题**：engine_distribution_matrix.md 第 69 行标记了一个关键事实——该函数有进程范围的 `umask` 行为，必须在 POSIX 系统上序列化。由于 libarchive 适配器在 Swift 中使用，在并发提取场景中，两个提取操作可能在 libarchive 内竞态争夺进程范围的状态。**架构必须指定提取的序列化边界——互斥锁、actor 或单线程提取调度器。**

4. **混合引擎的事务模型未指定**：minizip-ng 通过添加/移除 API 修改 ZIP，而 libarchive 使用流式重写。事务层宣称"将更改的条目物化到应用管理的工作区，重写到兄弟临时归档"。但 minizip-ng 的重写路径与 libarchive 完全不同——事务层需要为每个引擎实现不同的重写策略。**未指定适配器合同**——每个引擎适配器必须实现哪些事务操作？它们如何向事务层报告进度？

5. **7zz 辅助程序许可合规未解决**：Direct 构建配置捆绑签名的 ARM64 7zz 二进制文件。根据 LGPL，捆绑需要相应的源代码、构建信息和通知。架构文档承认了这一点但未指定合规包。**必须有一个具体的 LGPL 合规计划，然后才能批准 Direct 配置。**

## 架构反例与数据完整性风险

以下是根据当前规范对选项 A 架构提出的具体失败场景。每个场景都以"给定条件 → 失败模式 → 当前未指定的缓解措施"格式呈现。

### 风险 1：跨文件系统暂存（数据丢失）
- **场景**：用户打开存储在 FAT32/exFAT USB 驱动器上的 ZIP 归档，进行编辑，保存。事务层将暂存文件写入 `/tmp`（APFS），然后在源归档上调用原子 `rename()`。
- **失败**：`rename()` 在跨文件系统边界时静默失败（POSIX EXDEV）。事务层可能回退到复制+删除，这不是原子的。如果复制+删除过程中发生崩溃，结果不确定——源文件被删除了吗？暂存文件完整吗？
- **当前缓解**：架构文档提到"在可能时写入兄弟暂存文件"（architecture_options.md 第 129 行）。这意味着与源归档同目录——这是正确的本能。但并未规定"兄弟暂存"是强制要求还是尽力而为。**必须要求：暂存文件必须始终创建在与源归档相同的目录中。跨文件系统暂存是对原子性约束的违反。**

### 风险 2：暂存写入中途磁盘空间不足（数据丢失）
- **场景**：用户向 40GB ZIP 添加一个 2GB 文件。事务层开始将新的 42GB 暂存归档写入包含源归档的卷。磁盘空间在写入 35GB 后耗尽。
- **失败**：部分暂存文件保留在磁盘上。源归档未受影响（正确），但：(a) 部分暂存文件消耗了宝贵的磁盘空间；(b) 如果暂存文件名与源归档名冲突（例如 `archive.zip.staging`），用户可能混淆两者；(c) 如果在清理暂存文件之前重新启动应用，应用可能尝试恢复或误读暂存文件。
- **当前缓解**：架构文档提到"自由空间预检"（architecture_options.md 第 128 行）但未指定如何估计——归档可以压缩，因此"源大小 + 新条目大小"可能不足。**必须要求：预检必须从引擎获取未压缩总大小估计值并添加安全余量（例如 2 倍）。部分暂存文件必须具有可区分的命名方案，并在下次启动时清理。**

### 风险 3：暂存期间源归档 TOCTOU（静默损坏）
- **场景**：用户打开 ZIP 归档并开始编辑。在编辑期间，外部进程（例如备份守护进程、同步工具）修改源归档。用户保存。事务层检测到源自打开以来已更改。
- **失败**：检测机制是什么？如果使用 mtime，macOS HFS+ 的 mtime 粒度为 1 秒——在同一秒内的更改无法被检测到。如果使用 inode，外部替换（写新文件 + 重命名）会改变 inode。如果使用校验和，校验和整个 50GB 归档的代价过于高昂。**如果检测失败，事务层会将用户的编辑应用到过时的归档版本上，静默丢弃外部更改。**
- **当前缓解**：架构文档提到"检测源更改"（architecture_options.md 第 129 行），但完全未指定检测机制。**必须要求：指定 inode + mtime + 大小作为最低成本的更改指示器；声明当检测失败（例如 mtime 粒度冲突）时，应用在保存前警告用户归档已被外部访问。**

### 风险 4：嵌套归档递归爆炸（DoS）
- **场景**：用户打开包含 100 个 ZIP 文件的 ZIP，每个 ZIP 又包含 100 个 ZIP 文件，10 层深。归档浏览器尝试自动索引所有嵌套归档。
- **失败**：内存/文件句柄耗尽，应用无响应。或者如果嵌套归档被延迟打开，用户点击 10 层深的 ZIP 会触发 10 个嵌套提取，可能耗尽可能的临时空间。
- **当前缓解**：架构文档用"嵌套归档"（nested-archive）标记了此风险（在会议上下文中），但架构选项文档未包含递归限制或嵌套深度上限。**必须要求：浏览树的递归深度上限（例如 4 层）；每个嵌套归档在显式用户操作前延迟打开；嵌套打开计入全局资源限制。**

### 风险 5：预览缓存路径遍历（沙箱逃逸）
- **场景**：恶意 ZIP 包含名为 `../../../../tmp/evil` 的条目。预览系统将该条目提取到隔离缓存中。路径解析在缓存根目录外解析。
- **失败**：提取的文件被放置在 `/tmp/evil` 而不是隔离缓存中。如果 Quick Look 随后在该文件上运行且文件是可执行的，恶意代码可能通过 Quick Look 的预览生成器运行。
- **当前缓解**：架构文档提到"防止 Zip Slip/路径遍历"（architecture_options.md 第 133 行），但它是作为一般安全层提到的，并非专门绑定到预览缓存。**必须要求：预览缓存提取必须拒绝任何规范化路径逃逸出缓存根目录的条目。拒绝在 UI 中报告为"blocked: path traversal"而非静默跳过。**

### 风险 6：RARLAB `rar` 发现注入（供应链）
- **场景**：用户在 PATH 中安装了恶意 `rar` 二进制文件，优先级高于合法的 RARLAB 安装。应用发现并执行它。
- **失败**：恶意 `rar` 可以窃取正在创建的归档内容、修改输出、或将有效载荷注入"合法"RAR 归档。
- **当前缓解**：架构选项文档声明应用"验证该提供程序"（architecture_options.md 第 13 行），但未指定验证机制。**必须要求：RARLAB 发现必须使用白名单路径（`/usr/local/bin/rar`、用户配置的路径），而非未限定 PATH；必须通过代码签名检查或校验和验证二进制文件；必须在首次使用时进行实时创建/测试探测以确认输出与预期匹配。**

### 风险 7：7zz 输出解析注入（UI 损坏/误导）
- **场景**：7zz 输出包含恶意构造的文件名（例如包含换行符、终端转义码或 Unicode 右到左覆盖字符的文件名）。解析器提取此文件名并在 UI 表格中显示。
- **失败**：换行符导致解析器将单个条目误解为两个条目。RTL 覆盖字符使文件名在 UI 中显示为镜像。转义码（如果传递到终端日志）可能扰乱日志输出。
- **当前缓解**：未提及。架构文档声明辅助程序输出被"结构化错误映射"和"有界输出"处理，但未指定文件名清理。**必须要求：所有从外部辅助程序输出解析出的条目名称在存储在领域模型中之前，必须剥离控制字符、规范化 Unicode 并验证长度；解析器必须拒绝具有嵌入换行符或非法代理项的条目。**

### 风险 8：7zz 版本偏差（隐蔽失败）
- **场景**：应用捆绑 `7zz` 26.01 并围绕其行为构建。用户在系统 PATH 中安装了 `7zz` 27.00，应用在 Local 构建中发现并使用该版本。`7zz` CLI 在 27.00 中更改了列出格式，破坏了解析器。
- **失败**：归档浏览显示空列表或错误计数，误导用户认为归档为空。
- **当前缓解**：架构文档未指定版本兼容性合同。**必须要求：辅助程序发现必须检查版本号并仅匹配受支持的版本范围（例如 `>=26.01, <27.00`）；在 Direct 构建中，捆绑的二进制文件固定版本；在 Local 构建中，版本不匹配时回退到捆绑/内嵌的二进制文件。**

### 风险 9：暂存文件清理失败（磁盘空间泄漏）
- **场景**：应用在事务保存期间崩溃，留下部分暂存文件。应用重新启动。暂存文件保留在磁盘上，从未被清理。经过多次崩溃循环，累积了 GB 级的垃圾文件。
- **当前缓解**：架构文档提到"有界恢复记录"（architecture_options.md 第 130 行），但未指定清理机制。**必须要求：应用启动时扫描已知暂存位置中的孤立暂存文件；早于 N 天的孤立文件自动删除；较新的孤立文件触发恢复提示（"找到未完成的保存……"）。**

### 风险 10：并发 7zz 进程争用临时空间
- **场景**：用户同时提取两个大型加密归档。两个操作都启动 `7zz` 进程，这些进程可能会在 `$TMPDIR` 中创建临时文件。
- **失败**：如果两个 `7zz` 进程使用重叠的临时文件名或超过 `/tmp` 配额，一个或两个提取失败。
- **当前缓解**：未指定。**必须要求：每个 7zz 调用接收隔离的 `TMPDIR`；辅助程序运行器在调用前创建唯一的临时目录，并在进程退出后清理。同时辅助程序操作的最大数量应设上限（例如 4 个并发提取）。**

## Windows 兼容证明门槛

W0/W1/W2 合同（windows_interoperability_contract.md）结构合理，但在实施前需要为每个声明提供最低物理证据。

### 当前合同声明的逻辑测试

**W0 — `传给 Windows 用户` 预设：**
- 声明："未加密 ZIP、Store 或 Deflate、UTF-8 加位 11、无 AppleDouble、NFC 规范化、无保留名称、Windows Explorer 原生打开。"
- **测试 1**：位 11 UTF-8 由 minizip-ng 和 ZIPFoundation 都支持。但 Windows Explorer 实际上对位 11 的遵守程度如何？在没有 Unicode 路径额外字段的情况下，Windows Explorer 是否仅依赖位 11？**需要证据**：在 Windows 11 24H2 上使用仅包含位 11（不含 Unicode 额外字段）的中文名称 ZIP 进行物理测试。推理不足以代替。
- **测试 2**：NFC 规范化与 macOS 行为。macOS 的 APFS 文件系统使用 NFC 规范化（某种变体），但在旧版 HFS+ 卷上创建的文件可能是 NFD。当用户从 Finder 拖放时，文件名已经是 NFC 了吗？还是在归档创建器内需要显式的 NFC 规范化？**需要证据**：使用 NFD 源文件名创建 ZIP，验证输出文件名在十六进制级别上确实是 NFC。
- **测试 3**：路径冲突检测。合同声明"在创建前检测规范化等效冲突和 Windows 大小写不敏感冲突"。检测后会发生什么——错误？警告？自动重命名？用户选择？**合同对冲突解决保持沉默。**
- **测试 4**：保留名称。Windows 保留 CON、PRN、AUX、NUL、COM1–COM9、LPT1–LPT9，不带扩展名或带有任意扩展名（例如 `CON.txt` 也被保留）。macOS 允许创建 `con.txt`。**合同未指定保留名称列表、检测范围（仅最终组件 vs 完整路径）或冲突解决。**
- **测试 5**：路径长度。Windows MAX_PATH 在注册表修改前为 260 个字符（完整路径），但在启用长路径时可达 32,767。W0 应针对哪个？**合同未指定路径长度限制。**

**W1 — 加密合同：**
- 声明："AES ZIP 在 Windows 上需要兼容的第三方解压软件"。
- **问题**：哪个 Windows 第三方解压软件支持 minizip-ng 生成的 AES ZIP？7-Zip 支持 WinZip AES（AE-1 和 AE-2）。WinRAR 支持。但 Windows 内置支持不支持。**合同正确，但应明确命名："需要通过 7-Zip 或 WinRAR"。**
- ZipCrypto：已知存在已知明文攻击漏洞。合同正确标记为"保护较弱"。但用户可能不理解"较弱"的含义——标准是否足以抵御随意窥探？是的。是否能抵御有动机的攻击者？不是。**建议：ZipCrypto 标签应链接到解释确切威胁模型的应用内帮助。**

**W2 — 专家格式：**
- 声明：TAR.ZST 列在"长期归档"预设中。
- **问题**：Zstandard 在归档场景中相对较新。Windows 11 24H2 的 `tar` 命令是否支持 Zstandard？需要验证。当前的 `tar` 文档可能不支持 Zstandard 解压。**对 TAR.ZST 的 W2 声明需要物理验证。**

## RAR 创建启用门槛

RAR 创建在当前证据下是一个已正确识别的缺口：不存在合法的开源 RAR 编码器。用户已批准"仅当存在合法开源选项"以及可选的"单独安装/许可的 RARLAB"。以下是从设计到实施前必须满足的确切门槛。

### 启用条件（逻辑 AND）

1. **提供程序发现**：应用在用户明确配置的路径中发现 RARLAB `rar` 可执行文件。不得使用未限定的 PATH 解析（供应链风险——见风险 6）。
   - **证据**：源代码显示使用绝对路径或白名单目录；`which`/`command -v` 未在没有用户确认的情况下使用。

2. **二进制验证**：应用验证已发现的二进制文件：
   - 其代码签名证书链有效，主题组织 (`codesign -dvvv`) 匹配 "win.rar GmbH" 或 RARLAB 预期的签名身份。
   - 备选方案（如果未签名）：SHA-256 校验和对照已知良好值表——但这需要可信的校验和来源。由于 RARLAB 分发未经公证的二进制文件，代码签名是更可靠的验证。
   - **不确定性**：RARLAB 的 macOS ARM `rar` 二进制文件是否经过代码签名？当前来源中未建立证据。**在签署 RAR 创建设计之前必须解决此问题。**

3. **许可确认**：用户看到 RARLAB 许可条款并明确确认：
   - 他们拥有使用 `rar` 的单独许可（或处于 40 天试用期内）。
   - 他们理解该应用不重新分发 `rar`——它仅使用现有安装。
   - 确认是持久的（用户默认设置），而非每次保存都需要。
   - **证据**：许可确认 UI 的线框图；持久设置键值与最后一轮确认时间戳。

4. **实时创建探测**：在将任何用户数据委托给 `rar` 之前，应用运行一个实时测试：
   - 使用已知内容（测试字符串、随机载荷）创建测试 RAR 归档。
   - 验证：（a）`rar` 以退出码 0 退出；（b）输出文件存在且非空；（c）归档可以被应用的 RAR 读取器（7zz）列出；（d）提取的测试内容与原始内容匹配。
   - 如果探测失败（`rar` 崩溃、输出为空、提取不匹配），RAR 创建能力被标记为不可用，并附解释性错误。
   - **证据**：探测逻辑的源代码；失败模式 UI。

5. **构建配置分离**：
   - Local 构建：可能发现外部 `rar`。应用偏好设置中提供启用 RAR 创建的开关，默认关闭。
   - Direct 构建：同上。`rar` 二进制文件从不捆绑。
   - OpenSource 构建：RAR 创建设置存在但始终显示"需要 RARLAB rar 安装"。无自动发现，以防止对许可条款的混淆。构建者/用户必须显式配置路径。
   - **证据**：显示 RAR 创建开关和按构建配置变体的 `ArchiveCapabilityRegistry` 初始化代码。

### RAR 创建相关的不确定性

- RARLAB macOS ARM 二进制文件的代码签名状态。**未知**——在批准涉及 RARLAB 提供程序验证的设计元素之前，需要物理检查当前 RARLAB 下载。
- RAR 5.0 与 Windows 11 Explorer 原生的兼容性。微软声明 Explorer 支持 RAR，但未指定 RAR4 还是 RAR5。**需要物理验证**。如果 Explorer 仅支持 RAR4（而非 RAR5），产品必须反映此限制，可能将 RAR5 降级到 W1。

## LOOP 记录

### 操作
1. 读取全部 6 个指定输入文件（context、initial_landscape、engine_distribution_matrix、windows_interoperability_contract、architecture_options、codex_review）。
2. 根据每个用户批准的需求和已批准格式矩阵的完整性、范围缩减和可实现性，对选项 A/B/C 进行审判。
3. 构造了 10 个具体的架构失败场景，涵盖数据丢失、TOCTOU、路径混淆、解压炸弹、嵌套归档、密码/加密、文件系统边界、供应链和恢复。
4. 对 W0/W1/W2 Windows 兼容合同的每个声明进行了逻辑测试，识别了缺失的规范（冲突解决、路径长度、保留名称列表），并制定了每个声明的物理证据表格。
5. 定义了 RAR 创建的 5 个启用条件（发现、验证、许可、探测、构建配置分离）。
6. 构建了将 12 个用户需求映射到具体证明门槛、当前状态和差距的实现前证明矩阵（G1–G12）。
7. 生成了按优先级排序的必须修订项列表：5 个 P0（签署阻塞项）、7 个 P1（设计阶段）、5 个 P2（实施前）。

### 观察
- 选项 A 的三个引擎（minizip-ng、libarchive、7zz）对于多个格式存在能力重叠。这创造了灵活的回退路径，但也导致了在当前规范中完全未指定的不确定路由。这是 P0 差距。
- 事务模型是合理的——暂存/验证/fsync/原子替换——但在跨文件系统行为上存在静默故障模式，而当前架构文档对"兄弟暂存"使用许可性语言（"尽可能"）而非强制性语言。这可能在外部驱动器上造成数据丢失。
- libarchive 的 `umask` 序列化要求（engine_distribution_matrix.md 已正确标记）是一个重要的实现约束，可能在多线程 Swift 代码中被忽略，引发难以调试的文件权限错误。
- W0 合同经过深思熟虑，但存在三个阻止实施的空白：保留名称的冲突解决行为、路径长度限制以及仅位 11 UTF-8（无 Unicode 额外字段）是否被 Windows Explorer 接受的物理证据。
- RAR 创建架构已正确限制，但提供程序验证假定代码签名检查没有证据表明 RARLAB 的 macOS 二进制文件确实已签名。这是一个需要物理解决的不确定性，然后才能签署验证设计。
- LGPL 合规对于 Direct 构建配置是一个重要的未解决问题。捆绑 `7zz` 需要源/构建/通知包，而该包在当前工作产品中未指定。
- 必须修订项列表是完整的且优先级已正确分级。P0 项是真正的阻塞项——如果不解决，选项 A 在其关键路径上存在可证明的差距。

### 评估
- **选项 A 在当前状态下尚不可批准**。其核心架构方向是正确的，但以下方面存在特定、可证明的差距：多引擎路由、跨文件系统事务原子性、预览缓存安全性和 TOCTOU 检测。
- 这些差距并未推翻选项 A——它们代表了在签署设计规范之前必须解决的工程细节。选项 B 和 C 被正确拒绝，理由比架构选项文档中提出的更强。
- W0/W1/W2 合同结构合理，应作为接受标准基础予以保留。缺失的部分（冲突解决、路径长度、保留名称列表）是合同空白，而非逻辑错误。
- RAR 创建的 5 条件门槛比架构文档中当前的"单独安装/许可"模糊声明更强。此门槛应在最终设计规范中采用。
- 总体证据成熟度：引擎可行性（高）、安全设计（中等——已识别威胁但未指定防御措施）、跨平台验证（无——未配置 Windows VM）、UI 实现（无——未安装完整 Xcode）。

### 拟议修订
1. 将 P0-1 至 P0-5 作为阻塞项纳入最终设计规范签署清单。
2. 提升"兄弟暂存"从"尽可能"变为事务层的硬性要求。
3. 要求编码引擎适配器协议（P1-1），然后才能批准任何引擎集成设计。
4. 将 RAR 创建 5 条件门槛（发现、验证、许可、探测、构建配置分离）纳入规范。

### 不确定性
- RARLAB macOS ARM 二进制文件的代码签名状态——在代码签名依赖的验证设计获得批准之前，需要进行物理检查。
- Windows 11 24H2 `tar` 的 Zstandard 支持——在获得物理证据之前，TAR.ZST 的 W2 声明仍然是推测。
- 仅位 11 UTF-8（无 Unicode 额外字段）的 Windows Explorer 行为——需要物理证据。minizip-ng 可以写入两种形式，但合同应规定对于 W0 哪种形式更安全。
- 完整 Xcode 不可用意味着 Liquid Glass 合规性和构建配置验证仍然是纸上设计，而非已验证的实现约束。
