## 2. 逐项反证核查

### 2.1 提取/预览比例预算与覆盖边界

**规格条款**：§11.5（预览）、§12（解压缩）

**证据**：
- 预览路径：每文件 256 MiB / 每窗口 1 GiB / 30 秒硬上限；单条目解压比 > 50:1 时阻断，标注「此项目的压缩比例异常，请解压缩后查看」。规格原文：「该预览比例限制不可覆盖」——明确禁止覆盖。
- 解压缩路径：总体或任一条目解压比 > 100:1 先阻断；用户可在重新确认目标空间、展开大小和风险后对显式解压缩单次覆盖。预览覆盖仍禁止。
- 默认阻断阈值：50 GiB / 目标空闲 80% / 1,000,000 项 / 路径深度 128 / 解压比 100:1。收紧允许，放宽需安全评审。

**是否闭合**：是。预览不可覆盖与解压可单次覆盖的边界清晰，比例分级（50:1 vs 100:1）合理。无矛盾。

**裁决**：PASS（无 P0/P1）。

---

### 2.2 7zz 人类可读输出非权威、隔离暂存与 fd 根后验证

**规格条款**：§12.1「外部引擎安全契约」、§16「外部提供方与进程模型」

**证据**：
- §12.1 明确规定 7zz stdout/stderr「只用于诊断，绝不作为路径安全、成功或完整性的唯一数据源」。
- 加密/特殊 7z 或 RAR 始终先解到仅该任务可访问的随机暂存根；helper 不获得最终目标写权限。
- 应用以文件描述符为根、不跟随链接地枚举实际产物，逐项执行包含性检查。任何越界产物、控制字符、未知节点类型、输出截断、版本协议不匹配或预算超限均整单失败并清理暂存。
- §16 每任务独立 `0700` 工作目录；不使用 shell；stdout/stderr 环形缓冲溢出即终止，不以截断输出判断成功。

**是否闭合**：是。人类可读输出的非权威性已明确声明，暂存隔离路径完整，fd 根验证覆盖了路径遍历与 TOCTOU 风险。

**P2 注意**：fd 根验证（`openat`/`fstatat` 语义）的正确性依赖实现质量，规格已指出正确方向；环形缓冲大小未指定，需实施调优。

**裁决**：PASS（P2 记录见 §3）。

---

### 2.3 RARLAB 签名/信任与输出验证

**规格条款**：§16.1「RARLAB」

**证据**：
- 解析符号链接后验证：常规文件、Apple Silicon、所有者为用户/root、组/其他不可写。
- 执行前使用 Security.framework 静态代码 API 验证签名有效性（非 ad-hoc），签名链/Team ID 与「项目维护的已验证 RARLAB 发布者清单」匹配。不满足则 v1 RAR 创建保持禁用，不以版本字符串替代。
- 显示许可证、签名身份和 SHA-256，用户确认。
- 隔离探测阶段：在随机探测目录中执行创建/检测/解压并核对哈希。该步骤不证明后续输入可信——真实任务仍受通用进程模型和暂存发布限制。
- 通过条件：`rar` 成功 + `rar t` 无错 + RARLAB 自身解压 → 条目清单/大小/SHA-256 与输入一致 + 固定版本 `7zz` 独立列举/解压一致。任一步失败不发布。
- 路径/身份/签名/版本/SHA-256 变化自动禁用，要求重新验证。
- RARLAB 二进制不复制到任何分发物。

**是否闭合**：是。多层验证链（文件属性 → 代码签名 → 发布者匹配 → 隔离探测 → 双引擎交叉验证）是纵深防御。失败自动禁用且不降级。

**P2 注意**：RARLAB 发布者清单的维护流程和初始种子未在规格中定义，运营层面需配套机制。

**裁决**：PASS（P2 记录见 §3）。

### 2.4 钥匙串在重命名/移动/复制/编辑下的稳定关联

**规格条款**：§18「密码与钥匙串」

**证据**：
- 钥匙串密码项使用随机 UUID 主键。本地元数据仅保存：用户标签、安全作用域书签、卷/文件资源标识、创建时间、内容指纹。**密码不保存在元数据中。**
- 打开流程：先解析书签并匹配文件资源标识；同卷重命名/移动后更新书签。
- 精确内容指纹仅用于识别未改变的复制件。编辑保存成功后在同一密码项追加新指纹并淘汰旧的"当前位置"关联。
- **资源标识与指纹都不匹配时不自动尝试任何候选密码**——提示重新输入，允许用户明确关联。网络卷、备份恢复和复制场景必须经过该保守分支。

**是否闭合**：是。双重匹配（资源标识 + 内容指纹）加保守回退是正确策略。重命名/移动的书签更新、编辑后的指纹追加均覆盖。

**裁决**：PASS（无 P0/P1）。

### 2.5 TOCTOU/文件协调、恢复 HMAC、分卷快照、Helper 隔离与扩展 IPC

**规格条款**：§14.2、§14.4、§15、§16、§20、§30

#### 2.5.1 TOCTOU / 文件协调

- §14.2 步骤 6-8：`NSFileCoordinator` 包裹源复核和原子替换在同一协调写入块。块内重新检查设备/文件身份/大小/纳秒时间戳和 SHA-256。源变化则中止。原子替换后释放协调再验证。
- **已知局限**（非规格缺陷）：`NSFileCoordinator` 仅协调其他 `NSFileCoordinator` 使用者，不阻止 Terminal `mv`/`cp` 或非协调应用。SHA-256 复核在协调块内执行，最小化了窗口。这是 macOS 平台限制，不是规格矛盾。

#### 2.5.2 恢复 HMAC

- §15：恢复日志存于应用支持目录，仅记录安全作用域书签、源指纹、暂存身份、操作和阶段，不记录密码。
- 每条记录使用钥匙串内随机本机密钥做 HMAC。验证失败 → 隔离并记录诊断，**绝不恢复或提交**。
- 启动扫描未完成事务，**永不自动提交**。
- 源变化或暂存损坏 → 仅保留/删除，不覆盖源。

#### 2.5.3 分卷快照

- §14.4：分卷不能原子替换 → 同级事务目录生成/验证完整分卷后以新基名发布。编辑已有分卷始终「另存为…」。
- §20：分卷发现按格式规则生成候选；每卷记录文件资源标识、大小、修改时间和 SHA-256。操作前全部复核。身份变化/编号缺口/重复卷/越权 → 停止并要求确认。

#### 2.5.4 Helper 隔离

- §16：每任务 `0700` 工作目录；全局最多 2 外部任务，同压缩包仅 1 修改。无 shell、显式 argv、选项终止保护、最小环境。stdout/stderr 环形缓冲溢出终止。取消先温和后强制（3 秒超时，§23）。版本/架构/身份/输出协议全部匹配。

#### 2.5.5 扩展 IPC

- §30：Quick Look / Finder / App Intents 扩展使用独立 App Sandbox、只读/用户选择授权、独立容器。扩展不得执行 7zz/RARLAB、不得获得主应用任意文件权限、不通过共享可执行代码绕过沙盒。
- 主应用与扩展仅经由版本化、类型化 App Group 请求/结果文件或系统 extension API 交换最小元数据。请求含：随机 ID、输入书签/只读文件协调信息、期限、**签名/HMAC**。主应用重新授权并重新验证后才执行。
- 扩展失败 → 回退为「在归档工作台中打开」，不放宽 entitlement。

**是否闭合**：是。五个子维度均有完整设计。

**P2 注意**：
- 扩展 IPC 的 HMAC 密钥建立机制未在规格中明确（可通过 App Group 共享钥匙串实现，但规格未声明）。
- `NSFileCoordinator` 不防非协调写入者——这是 macOS 固有局限，规格通过协调块内 SHA-256 复核做了最大缓解。

**裁决**：PASS（P2 记录见 §3）。

### 2.6 P0/P1 分类总结

#### P0（规格矛盾或必然导致漏洞的缺陷）：0 项

未发现规格内部矛盾。未发现若按书面实现必然产生可利用安全漏洞的设计。

#### P1（实施前须关闭的规格空缺）：1 项

| # | 标题 | 涉及条款 | 说明 |
|---|---|---|---|
| P1-01 | **密码跨界传递机制未正向规定** | §18 + §16 | §18 明确禁止密码出现在 argv（「不得把密码放进 argv」），但未正向规定 7zz/RARLAB helper 接收密码的安全机制。7zz 支持通过 stdin 读取密码（`-p` 无参或 `-p-`），也支持通过环境变量和文件。规格仅要求「C/CLI 适配器只在最短作用域创建本地缓冲，使用后显式清零」，未规定进程间传递通道。**风险**：若实施选择环境变量（可被子进程继承/通过 `ps` 泄漏）或临时文件（磁盘残留），将产生漏洞。**建议**：规格应明确要求使用 stdin pipe 或受控 pipe fd，禁止环境变量和临时文件传递。在实施密码处理代码前必须关闭。 |

#### P2（实施细节/运营关注，不阻断计划编制）：4 项

| # | 标题 | 涉及条款 | 说明 |
|---|---|---|---|
| P2-01 | 扩展 IPC HMAC 密钥建立机制未声明 | §30 | 主应用与扩展之间的 HMAC 签名需要共享密钥。App Group 容器或共享钥匙串是可行路径，但规格未说明初始密钥如何协商/存储。实施计划应记录此决策。 |
| P2-02 | RARLAB 发布者清单维护流程 | §16.1 | 规格要求签名链/Team ID 匹配「项目维护的已验证 RARLAB 发布者清单」，但清单的初始种子、更新频率和完整性保护机制未定义。若 RARLAB 轮换签名身份而未及时更新清单，RAR 创建功能将不可用（安全降级为禁用——正确行为），但恢复流程未说明。 |
| P2-03 | 7zz 版本范围未量化 | §16 | 规格要求「版本范围、架构、身份和输出协议均需匹配」，但未定义可接受的版本范围（精确匹配？最小版本？语义化版本范围？）。Direct 构建需要固定已知版本；Local 构建需定义可接受范围。 |
| P2-04 | `NSFileCoordinator` 不防非协调写入者 | §14.2 | 这是 macOS 平台固有局限，规格通过在协调块内执行 SHA-256 复核做了最大缓解。不需规格级修改，但实施计划和测试矩阵应显式记录此限制，并确保故障注入测试覆盖非协调外部修改场景。 |

## 4. 裁决详情

### GO / NO-GO：条件性 GO

**理由**：
- 规格 v0.10 在设计层面闭合了 QC-3 六项安全阻断项，防御纵深完整。
- 未发现规格级矛盾（P0）。
- 密码跨界传递机制未正向规定（P1-01），**必须在实施密码处理代码前由 Codex 关闭**。该空缺规格化后不改变整体安全架构，不影响其他模块的实施计划编制。

### 建议
1. **立即**：在实施计划中记录 P1-01 的关闭方案（推荐 stdin pipe，禁止环境变量和临时文件）。
2. **实施计划阶段**：将 P2-01 至 P2-04 记录为实施计划的「待关闭设计决策」项，按各自依赖的模块排期。
3. **Xcode spike 后**：重新审查 DMG 挂载与 App Sandbox 交互（§17 与 §30 的依赖，当前规格已有诚实降级路径）。

### 不确定性声明
- 本审查仅基于书面规格；不验证实现正确性。
- `NSFileCoordinator` 针对非协调写入者的局限性是 macOS 平台固有问题，规格已做最大缓解；物理测试矩阵需覆盖此场景。
- RARLAB 发布者清单的初始种子需通过独立渠道验证（不能依赖本审查建立信任）。
- 本文不声称对视觉、中文术语、Windows 互操作或性能预算的权威判断——这些属于其他 QC 参与方的范围。
