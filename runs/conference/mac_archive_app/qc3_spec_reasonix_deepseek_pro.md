## 实施计划 Go/No-Go

**判定：NO-GO — 在 5 项 P0 问题解决前不得进入实施计划。**

规格在架构层面达到 0.9 版应有的深度，安全态势设计总体正确（无 shell、暂存—验证—原子替换模型、路径白名单校验、隔离预览），**但存在 5 项阻断级安全与设计缺陷**（见下文 P0 列表），每项均可单独导致实施后出现不可恢复的数据损坏、密码丢失或供应链攻击。

P0 问题全部属于以下三类之一：
1. **可量化的安全漏洞**——攻击者可构造输入绕过现有防御。
2. **不可逆的数据/密钥丢失路径**——设计歧义导致实施后必然出错。
3. **关键特征完全缺失**——规格许诺了能力但未定义该能力的任何设计约束。

P0 问题的共同特征是：无法通过"实施时再细化"来安全地推迟——它们在架构层面就需要决策，且决策错误无法通过后续补丁在不破坏兼容性的前提下修复。

## 数据损坏与安全反例

以下每个场景均以"攻击者/故障如何绕过规格给出的防御"来组织。

### 攻击场景 A：解压炸弹绕过项数/大小检查

**攻击方法**：构造一个 ZIP 文件——1 个条目，压缩后 50 MB，解压后 500 GB（10,000:1 比例）。

**规格声称的防御**（§12 第 4–5 步）：
- 阻断阈值：>50 GiB 输出 或 >1,000,000 项 或 路径深度 >128

**绕过**：1 个条目（≪ 1M），500 GB 输出（触发 50 GiB 阈值… 等等，500 GB > 50 GiB，所以会被阻断。让我重新设计）。

**修正后攻击**：1 个条目，压缩后 50 MB，解压后 40 GiB。40 GiB 低于 50 GiB 阈值，1 条目远低于 1M 项。但 50 MB → 40 GiB 的比例是 800:1——典型的炸弹特征。

**防御缺口**：规格的阻断阈值是绝对大小（50 GiB）、绝对项数（1M）、绝对深度（128）。**没有任何阈值是基于压缩比的**。这意味着所有"压缩后小、解压后接近但不超过 50 GiB"的炸弹全部漏过。

**证据**：规格 §12 第 4 步写道："估计条目数、展开大小、**压缩比**、路径深度和可用空间"——压缩比被列为估计项，但 §12 第 5 步的阻断阈值仅包括大小、项数、深度，不包括比例。第 5 步原文："预计输出超过 50 GiB 与目标可用空间 80% 中较小者、超过 1,000,000 项、路径深度超过 128。"

→ **P0#1**

### 攻击场景 B：预览缓存炸弹

**攻击方法**：构造一个条目——压缩后 1 MB，解压后 200 MB，但使用高度重复的数据使得压缩比看起来正常。不，更简单的方法是构造 5 个条目，每个压缩后 1 MB，解压后 250 MB。

**规格声称的防御**（§11 第 5 步）："受每文件 256 MiB、每窗口 1 GiB、30 秒及解压比例预算约束"

**防御缺口**：256 MiB、1 GiB、30 秒均被量化。但"解压比例预算"——规格的关键反炸弹措施——**从未被赋予数值**。它是规格中的唯一未定义阈值。

如果实施者将比例默认设为 100:1，则 1 MB → 250 MB（250:1）被阻断。但如果实施者忘记实现比例检查（因为规格从未定义它），或设为 1000:1，攻击成功。关键是：**规格没有给出必须实现的数值**，因此实施者可能在无意中省略这层防御。

**证据**：规格 §11 第 5 步。

→ **P0#2**

### 攻击场景 C：通过 7zz 输出解析的路径穿越

**攻击方法**：构造一个 7z 压缩包，其中条目路径在 7z 内部表示为 `../../etc/passwd`。`7zz l -slt` 输出中将显示 `Path = ../../etc/passwd`。如果应用解析此输出时的路径校验逻辑有缺陷（例如只检查前缀 `/` 而非 `../`，或规范化处理在提取路径之前而非之后），路径穿越成立。

**规格声称的防御**（§12 第 2 步）："拒绝绝对路径、`..`、空组件、NUL、越界路径和目标根外的规范化结果"

**防御缺口**：该防御描述的是**应用层验证**，这很好。但规格没有区分**谁负责验证**——对于 ZIP（minizip-ng 库内处理），路径遍历可以由库的 API 层面阻止；对于 7z（通过 `7zz` CLI helper），应用必须解析 `7zz l -slt` 的文本输出以获取路径，然后自行验证。**CLI 输出解析用于安全决策是本审查识别出的最高风险实现模式**，因为：
1. `7zz` 的输出格式未在规格中定义（不同版本的 `7zz` 输出格式可能不同）。
2. 恶意构造的路径可能包含控制字符或 Unicode 技巧，在解析中出现意外的行截断。
3. 7z 格式本身支持一些 ZIP 不支持的特性（如空组件路径、超长路径），应用可能未处理。

**规格未定义**：7zz 输出解析契约、路径验证在解析前后的位置、恶意输出注入测试策略。

**证据**：规格 §16 定义了 helper 进程模型（无 shell、显式 argv、环形缓冲）但未定义**输出语义契约**。§12 定义了路径安全策略但未区分"库内路径 API"与"CLI 输出文本解析"两种完全不同的验证上下文。

→ **P0#3**

### 攻击场景 D：伪冒 RARLAB 二进制

**攻击方法**：提供一个恶意 Mach-O 可执行文件，文件名为 `rar`，Apple Silicon 架构，权限正确（用户所有，组/其他不可写），其 `--version` 输出伪造为 `RAR 7.01 ... Copyright (c) ... Alexander Roshal`。

**规格声称的防御**（§16.1）：
1. 解析符号链接
2. 验证常规文件、Apple Silicon、所有者为用户/root、组/其他不可写
3. 验证版本与 RARLAB 身份输出
4. 在临时目录执行创建、检测、解压缩探测并核对哈希

**绕过**：恶意二进制模拟所有输出。第 5 步的"创建、检测、解压缩探测并核对哈希"仅在恶意二进制愿意配合时有效。如果恶意二进制在探测中正常运作，但在用户后续的真实创建操作中执行恶意行为（时间炸弹型攻击），验证步骤无法检测。

**更深层的问题**：第 5 步**运行二进制以验证它**。如果二进制本身就是恶意软件，验证步骤就是攻击的执行点。规格未要求在此步骤中对二进制进行沙盒隔离。

**未实施的检查**：
- 无代码签名验证（`codesign -dvvv` 检查 RARLAB 签名）
- 无已知哈希白名单
- 验证步骤本身没有在独立沙盒中运行恶意二进制

**证据**：规格 §16.1；引擎矩阵确认 RARLAB 是专有软件，无开源替代。

→ **P0#4**

### 攻击场景 E：钥匙串标识符歧义导致密码不可恢复

**问题**：规格 §18 说密码存储使用"压缩包稳定标识和用户可识别名称"。但"稳定标识"未被定义。

**两个可能的设计方向及其各自失败模式**：

| 标识策略 | 优点 | 失败模式 |
|---|---|---|
| 文件路径 | 直观，用户理解 | 移动/重命名压缩包 → 密码丢失。用户不理解为何"同一个文件"不再识别 |
| SHA-256（或其他内容哈希） | 跨移动稳定 | **编辑压缩包会改变哈希** → 保存后密码丢失。用户保存了加密压缩包却发现自己的密码"不再匹配" |
| 文件 ID（inode/设备对） | 移动后仍有效（同一文件系统） | 跨卷移动、备份恢复、Time Machine → 失效。不可跨设备 |
| 混合：路径 + 哈希 + 文件 ID 模糊匹配 | 弹性最强 | 规格禁止："更换/移动文件导致标识不确定时不自动尝试多个密码" |

规格的禁止条款（"不自动尝试多个密码"）排除了混合模糊匹配策略，但未定义单一策略。**无论在实施中选择哪一种，都会在某些常见用户场景下导致不可恢复的密码丢失**。这是必须在设计阶段解决而非实施阶段发现的问题。

**证据**：规格 §18。

→ **P0#5**

### 更多安全反例（非阻断但需关注）

**F1. 保存 TOCTOU 窗口**（→P1#10）
规格 §14.2：第 6–7 步做 source identity/SHA-256 验证，第 8 步做原子替换。两步之间不是原子的。如果外部进程在第 7 步和第 8 步之间原地修改了源文件（不是替换 inode，而是写入修改），原子替换会覆盖外部修改。
- macOS 的 `-[NSFileCoordinator coordinateReadingItemAtURL:options:error:byAccessor:]` 可以在验证与替换之间持有协调锁——规格未要求使用。
- APFS 的 `replaceItem(at:withItemAt:)` 是原子的，但被替换的是验证时的 inode；如果该 inode 的内容在第 7–8 步之间被修改，那么修改会随 inode 被替换而丢失。

**F2. 恢复日志无完整性保护**（→P1#11）
规格 §15：恢复日志存储在应用支持目录，无签名、无 HMAC、无加密。如果日志被损坏或恶意修改（应用支持目录不需要 root 权限即可写入），启动时的恢复扫描可能触发未定义行为。尽管规格声明"永不自动提交"，但损坏的日志可能指向任意路径，造成混淆或文件系统扫描触发。

**F3. DMG 挂载恢复语义模糊**（非阻断观察）
规格 §17："启动时恢复应用遗留挂载"——是指重新挂载还是清理孤儿挂载？如果重新挂载，则在应用启动时自动挂载 DMG 的行为违背了"永不自动挂载"的安全约束（DMG 应仅在用户请求时挂载）。如果仅是清理，则措辞不当。

**F4. 多密码压缩包未处理**（非阻断观察）
ZIP 格式允许每个条目使用不同密码。7z 格式支持多密码。规格未定义如何处理——是否每个条目独立提示密码？首个错误密码即全局失败？

## 跨平台编码与大规模风险

### Windows W0 bit-11 UTF-8：引用假设 vs. 物理证据

Windows 合同（`windows_interoperability_contract.md`）将 W0 策略定义为："UTF-8 with general-purpose bit 11 in both local and central headers, without BOM."

该策略依赖于两个假设：
1. **假设 A**：Windows 11 24H2 Explorer 正确读取并显示 bit-11 UTF-8 文件名（而无需 Unicode Path extra field）。
2. **假设 B**：PKWARE APPNOTE 6.3.10 的"Unicode Path extra field not needed when bit 11 is set"声明在 Microsoft 的实现中成立。

**证据状态**：这两个假设在输入文件中均为**引用假设**，未经物理验证。引擎矩阵确认 minizip-ng 可以生成此格式。Windows 合同将其列为"not yet approved"。

**风险评估**：如果假设 A 不成立（即 Windows 11 Explorer 需要 Unicode Path extra field），则 W0 输出的文件名在 Windows 上显示为乱码。需要回退到写入 Unicode Path extra field（Info-ZIP 0x7075），规格将此列为"test candidate, not the W0 default"。这不影响压缩包内容正确性（仅影响文件名显示），但会破坏 W0 的用户承诺。**风险级别**：文件名显示故障，非数据损坏。建议在进入实施前至少完成一次本地 macOS→Windows 11 24H2 的 bit-11-only ZIP 传输烟雾测试。当前未关闭事项 §31 已将 Windows 测试环境列为未关闭——确保在宣称 W0 前完成。

### 遗留编码闭环：保存后编码策略缺失

规格 §9.2 定义 `ArchiveEntry` 有"原始路径字节与解码显示名分离"。打开 CP932 ZIP 时，原始字节保留，显示名使用 CP932 → Unicode 解码。

**但规约未定义**：当用户编辑此压缩包（添加/重命名条目）并保存时，**新条目的名称以何种编码写入**？

- 选项 1：始终 UTF-8（bit 11）。问题：与压缩包中已有的 CP932 编码条目不一致。
- 选项 2：使用与原压缩包相同的编码（CP932）。问题：新的 Unicode 名称如果在 CP932 中无等效字符，则丢失信息。
- 选项 3：保持每个条目的编码独立，新条目用 UTF-8。问题：混合编码 ZIP 在某些旧工具中可能显示异常。

规格对此沉默。→ **P1#9**

### ZIP64 / 4 GiB 边界：设计覆盖但实现细节开放

规格 §19 要求物理测试覆盖 ZIP64 和 4 GiB 边界。引擎矩阵确认 minizip-ng 支持 ZIP64。

**未在规格中处理的 ZIP64 细节**（实施级，非阻断）：
- 混合 ZIP32/ZIP64 条目（部分条目 <4 GiB 使用 32-bit 字段，部分使用 64-bit）的生成策略。
- ZIP64 EOCD 定位器/记录在被 ZIP 注释或其他尾部数据包围时的解析鲁棒性。
- 对于恰好 4 GiB − 1 字节的条目：使用 ZIP32 还是 ZIP64 字段？边界处的不一致选择可能导致互操作问题。

这些属于实施细节，但需要对 minizip-ng 的 ZIP64 行为做专门的边界测试——规格的测试计划（§28.1）未明确提及此项。

### 多卷 + W0 交叉沉默

规格 §13.1 的"发给 Windows 用户"预设包含：
- 未加密 ZIP、Store/Deflate、UTF-8 bit 11
- 分卷大小在 §5.3 创建面板中作为选项出现

**问题**：Windows 11 Explorer **不支持多卷 ZIP**（`.z01`, `.z02`, …, `.zip`）。如果用户选择"发给 Windows 用户"预设 + 分卷，生成的输出在 Windows 上无法原生打开。规格未禁止或警告此组合。

→ **P1#13**

### 路径深度检查的充分性

规格 §12 将路径深度 >128 作为阻断条件。此检查不充分：
- 128 层深度，每层 1 字符 = 总路径约 256 字符 → 可能 OK。
- 128 层深度，每层 200 字符 = 总路径 >25,000 字符 → 远超任何文件系统限制。

仅检查深度不足以防止路径溢出。需要同时检查总字节长度（或 UTF-16 code units 以适应 Windows 场景）。在规格的提取流程中，目标文件系统是 macOS（APFS，单组件 255 UTF-8 字节，总路径理论上 1024 字节），但结合路径深度检查+总长度检查更为安全。这是实施细节但值得在规格中明确。

## 构建许可证与发布边界

### Direct 配置文件：LGPL 合规未设计

规格 §26 要求 Direct 配置："捆绑 7-Zip 前必须提供对应源码、构建信息、修改记录和 LGPL/BSD/UnRAR 通知。"

LGPL §4 要求应用程序的用户能够重新链接 LGPL 组件（7zz）的修改版本。对于嵌入 `.app` bundle 的 helper 可执行文件：
- 最低合规：提供 7zz 的目标文件（`.o`）或构建脚本，使用户可以替换修改后的 7zz 二进制。
- 规格未说明如何满足这一要求——是通过文档说明替换路径，还是通过应用内置机制。
- 此外，7zz 内部链接的 UnRAR 代码带有额外的使用限制，这些限制必须单独披露。

→ **P2#16**

### Direct 配置文件：Hardened Runtime 授权未指定

规格 §26："Developer ID、hardened runtime、公证、嵌套代码签名"

对于生成外部进程的应用，至少需要：
- `com.apple.security.cs.disable-library-validation`：如果 7zz 链接了非系统库。
- `com.apple.security.cs.allow-unsigned-executable-memory`：某些压缩库可能使用 JIT 或自修改代码（对 minizip-ng/libarchive 通常不需要）。
- `com.apple.security.automation.apple-events`：如果应用需要 AppleScript/Finder 交互。

这些授权在 hardened runtime 审核中会触发额外审查。规格未定义应用所需的完整授权列表。

→ **P2#15**

### OpenSource 配置文件：可复现构建仅为声明

规格 §26："可复现依赖脚本或文档化外部 provider"

"可复现构建"是一个高门槛声明。至少需要：
- Swift Package Manager 的 `Package.resolved` 锁定文件。
- 外部 C 依赖（minizip-ng、libarchive、7zz）的固定版本/commit hash。
- 指定的 Xcode 版本和 macOS SDK 版本。
- 构建脚本中的确定性设置（`ZERO_AR_DATE=1`，无时间戳嵌入）。
- 字节级可复现的输出验证。

规格没有定义以上任何一项。当前"可复现"仅为意图声明。

→ **P2#17**

### 无上传边界：流程控制，非技术控制

规格的三处声明（§1、§2.2、§26）构成充分的文档边界。未实施技术执行（git pre-push hooks 等），在用户自安装场景下可接受。

## P0 P1 P2 必须修订项

### P0 — 阻断实施计划（5 项）

必须在编写任何实施计划或应用代码前解决。每项均附带建议的具体修订方向。

---

**P0#1** — 解压缩缺少解压比例阻断阈值

- **类型**：安全 — 炸弹检测不完整
- **受影响需求**：S-005
- **当前规格文本**：§12 第 5 步阻断阈值仅含大小（50 GiB）、项数（1M）、深度（128）
- **攻击演示**：1 条目 × 40 GiB 解压输出 × 50 MB 压缩输入 = 800:1，低于 50 GiB 阈值 → 炸弹漏过
- **建议修订**：在 §12 第 5 步增加「解压比例超过 100:1（默认值，待实测调优）时阻止；用户可经明确确认后覆盖」。同步在 §12 第 4 步的估计项中将「压缩比」提升为阻断条件而不仅是估计项。
- **不确定性**：100:1 是业界常见值（PeaZip 默认警报比例约 100:1），但 macOS APFS 的压缩行为可能影响此值的有效性——需在目标 Mac 上实测调优后最终确定。

---

**P0#2** — 预览解压比例预算未定义数值

- **类型**：安全 — 预览炸弹
- **受影响需求**：S-005（预览上下文）
- **当前规格文本**：§11 第 5 步「受每文件 256 MiB、每窗口 1 GiB、30 秒及**解压比例预算**约束」
- **攻击演示**：5 条目 × 各 1 MB 压缩 → 各 200 MB 解压，总计 1 GiB，每条目 <256 MiB，总窗口 = 1 GiB（触发阈值）。但如果每个优化到 250 MB（总共 1.25 GiB，超 1 GiB 被阻断），调整：4 条目 × 1 MB → 各 250 MB = 总计 1 GiB（恰好不触发窗口限制），比例 250:1。如果比例预算未定义/未实现，炸弹漏过。
- **建议修订**：在 §11 第 5 步明确：「解压比例预算：单个条目解压比超过 50:1 时跳过预览并提示『此条目压缩比例异常，建议解压缩后查看』；窗口级比例不做额外限制。」50:1 的理由：正常媒体/文档通常不超过 20:1；50:1 是保守但有辨别力的阈值。
- **不确定性**：50:1 假设需要在多种常见压缩包类型（JPEG 已压缩、文本、代码、办公文档）上验证不会误伤正常文件。

---

**P0#3** — 7zz CLI 输出解析安全契约未定义

- **类型**：安全 — 路径穿越
- **受影响需求**：S-002（路径穿越防御）、F-002（7z 操作）
- **当前规格文本**：§12 第 2 步定义了路径拒绝规则，§16 定义了进程模型，但二者之间的「7zz 文本输出 → 应用路径验证」契约完全缺失。
- **攻击演示**：7z 条目路径在 `7zz l -slt` 中以 `Path = ...` 行输出。恶意路径包含换行符注入（`../../\nPath = safe.txt`）可使朴素的行解析产生错误的路径提取。
- **建议修订**：在 §12 或 §16 中增加「7zz 输出解析契约」：
  1. 应用必须使用 `7zz l -slt -sccUTF-8` 固定编码。
  2. 路径解析使用严格的逐行状态机：仅接受 `Path = ` 前缀后的内容，直到行尾（`\n` 或 `\r\n`）。不接受多行或转义。
  3. 路径字段中出现的任何控制字符（U+0000–U+001F）导致该条目被拒绝并记录为 unsafePath。
  4. 路径验证在解析完成后、目标路径构造前执行（白名单：拒绝绝对路径、`..` 组件、空组件、Windows 保留名、目标根外结果）。
  5. 内部需备有已知版本 7zz 的输出格式变化记录；版本不匹配时的处理策略（警告？禁用？）。
- **不确定性**：`7zz l -slt` 输出格式是否为上游稳定契约，还是可能在小版本间变化——需要查上游文档确认。

---

**P0#4** — RARLAB 二进制验证不足

- **类型**：安全 — 供应链攻击
- **受影响需求**：S-009、F-009
- **当前规格文本**：§16.1 列出 7 步验证：符号链接解析、文件类型/架构/权限检查、版本输出验证、许可证确认、探测执行。
- **攻击演示**：恶意二进制通过所有 7 步；攻击在验证后的真实使用中才触发。
- **建议修订**：
  1. **增加代码签名检查**：` codesign -dvvv --verify /path/to/rar ` → 验证签名链中是否包含已知的 RARLAB 开发者身份。如果 RARLAB 不为 macOS 二进制签名（需要上游确认），至少验证二进制不被 ad-hoc 签名或未知证书签名。
  2. **沙盒化验证步骤**：第 5 步的探测在独立的一次性沙盒容器中执行，该容器仅可访问探测用的临时目录，无网络访问，无用户文件访问。
  3. **分离验证与使用**：明确区分——验证是一次性的受控探测；验证通过后，二进制用于实际操作时仍受 §16 的通用进程模型（无 shell、环形缓冲、取消、无用户文件之外访问）约束。
  4. 如果 RARLAB 不发布代码签名，则在规格中明确标注该外部依赖的信任级别：「依赖用户自行验证 RARLAB 二进制的真实性和完整性」——这与当前"用户明确选择或确认"语句一致，但当前规格模糊了应用验证与用户验证的界限。
- **不确定性**：RARLAB 是否为 macOS ARM64 二进制提供代码签名——需要查 RARLAB 当前分发实践。

---

**P0#5** — 钥匙串标识符策略未定义

- **类型**：设计 — 不可逆密码丢失路径
- **受影响需求**：W-013
- **当前规格文本**：§18「条目以压缩包稳定标识和用户可识别名称保存」
- **失败演示**：
  - 策略 = 文件路径 → 用户移动压缩包 → 密码丢失
  - 策略 = 内容哈希 → 用户编辑并保存加密压缩包 → 密码丢失
- **建议修订**：在 §18 中明确标识策略：
  1. 主标识 = `(volume UUID, inode, file size, birth time)` 四元组，在 APFS 上跨重命名稳定，跨移动不稳定。
  2. 当主标识不匹配时（移动后），回退到 SHA-256 匹配——但仅限**未编辑过的只读压缩包**。对于已编辑的压缩包，提示用户「此压缩包已被修改，钥匙串中的密码可能不再适用；请重新输入密码」。
  3. 用户可识别名称为用户提供的标签（默认使用压缩包文件名）。
  4. 将所有标识策略写入用户文档（设置 > 密码与钥匙串 中的说明文本）。
- **不确定性**：volume UUID + inode 策略在备份恢复（Time Machine）、网络卷和外部驱动器上是否稳定。需要在目标 macOS 版本上做验证。

---

### P1 — 高风险，必须在首个面向用户的构建前解决（8 项）

**P1#6** — 转换工作流完全缺失。§6.2 列出"转换"菜单项，F-013 要求转换支持，但全量规格中无任何转换流程设计（格式兼容矩阵、损失声明、预览、冲突处理）。**建议**：移除 §6.2 的转换菜单项，或将转换推迟到 v2 并明确标记为未实现，或补全设计。

**P1#7** — 设置面板内容为空。§5.5 列出 8 个分类但无内容。设置项（默认格式、默认解压目标、编码偏好、并发限制、临时目录策略等）与核心工作流交互，必须在实施前确定交互契约。**建议**：对每个分类定义至少 3 项具体设置及其默认值。

**P1#8** — 遗留编码检测/覆盖 UI 未设计。L-008 要求遗留编码支持，成熟产品研究（Bandizip、The Unarchiver）将其列为必备功能。规格 §9.2 仅分离了原始字节与显示名，未设计检测策略和用户覆盖入口。**建议**：增加编码检测策略（BOM 检测 → 启发式 → 用户默认）和设置面板中的编码覆盖 UI。

**P1#9** — 编辑后保存的编码策略未定义。当用户编辑 CP932 压缩包并保存时，新增/修改条目名称的编码选择不可逆。**建议**：定义策略——新条目始终使用 UTF-8（bit 11），与可能使用遗留编码的原有条目共存；在保存时若检测到混合编码，显示提示。

**P1#10** — 保存 TOCTOU 窗口。§14.2 第 6–7 步与第 8 步之间缺少文件协调锁。**建议**：在第 6 步前获取 `NSFileCoordinator` 协调读锁，在第 8 步后释放；或将第 6–8 步打包为单一 `coordinateWritingItem(at:options:error:byAccessor:)` 块。

**P1#11** — 恢复日志无完整性保护。**建议**：对恢复日志条目应用 HMAC（密钥派生自应用组标识符），启动时验证完整性；损坏条目记录诊断并跳过。

**P1#12** — Liquid Glass 无退化策略。Liquid Glass 是未发布的前瞻性 API。如果该 API 不存在、重大变更或在目标 macOS 上表现不同，规格需要定义视觉退化基线（例如回退到标准 toolbar/sidebar 材质，使用 `.ultraThinMaterial` + `.sidebar` 系统材质）。**建议**：在 §4.5 增加退化策略说明。

**P1#13** — 多卷 W0 组合无警告。**建议**：当用户同时选择「发给 Windows 用户」预设 + 分卷 > 0 时，显示「Windows 资源管理器无法直接打开分卷压缩包；接收方需要 7-Zip 或 WinRAR 才能解压」警告，且移除该组合的 W0 标签。

### P2 — 中等风险，在发布前解决（8 项）

**P2#14** — 无安装/升级/卸载流程设计。**建议**：在设计规格中增加「安装与升级」小节，定义 DMG 分发、首次启动体验、偏好迁移和卸载（移至废纸篓）策略。

**P2#15** — Direct 构建的 hardened runtime 授权未定义。**建议**：列出所需授权的最小集合，并提供每项授权的理由。

**P2#16** — 捆绑 7zz 的 LGPL 合规机制未设计。**建议**：定义 LGPL 再链接说明的提供方式（应用内致谢 + 构建文档），以及源码/构建脚本的分发方式。

**P2#17** — OpenSource 可复现构建仅为声明。**建议**：定义可复现构建的最低要素（锁定文件、固定版本、确定性设置），或降级声明为「构建文档化」而非「字节可复现」。

**P2#18** — 窗口尺寸约束缺失。**建议**：定义最小窗口尺寸（如 800×500 pt）和推荐的默认尺寸。

**P2#19** — 7z 注释与压缩包属性处理未提及。**建议**：定义是否/如何显示压缩包级别的注释和属性。

**P2#20** — DMG 原始提取功能未经能力测试定义。规格 §17 提到「原始提取仅在经过单独能力测试时启用」但未说明该测试包含什么。**建议**：定义能力测试的具体内容。

**P2#21** — 操作队列的优先级和暂停语义未定义。**建议**：在 §16 或 §21 定义队列行为：FIFO？用户可调整顺序？暂停/恢复？

## LOOP 记录

### 目标
对 `归档工作台` 全量设计规格执行 QC-3 反证审查——尝试证伪"规格安全且完整到足以进入实施计划"这一声称。

### 行动
1. 读取 8 个硬边界允许的输入文件（101,042 字节总计）。
2. 执行需求到规格交叉对照：将 RTM 60+ 需求 ID 逐条对应到全量规格的具体段落。
3. 构造 5 个对抗性安全反例场景（压缩炸弹、预览炸弹、7zz 路径注入、伪冒 RARLAB、钥匙串标识符歧义）。
4. 挑战每个数值阈值和自动行为（解压比例缺失、媒体阈值覆盖空白、编码自动检测缺失、路径深度检查单维度不足）。

7. 将发现分类为 P0/P1/P2 三级，给出 Go/No-Go 判定。

### 观察
- **架构层**：方案 A 的引擎路由清晰且已通过上游测试部分验证（minizip-ng 244/244、libarchive 1005/1005，63 项跳过已记录）。事务模型（暂存→验证→fsync→原子替换）总体正确。安全态势总体设计良好（无 shell、路径白名单、隔离预览、崩溃恢复）。
- **但存在 5 项 P0 缺口**：这些不是"需要更多细节"，而是规格中存在可被攻击者利用的空白。其中 3 项（P0#1、P0#2、P0#3）允许恶意构造的压缩包绕过安全防御；1 项（P0#4）允许供应链攻击；1 项（P0#5）导致用户的密码在某些常见操作后永久不可恢复。
- **P1 项中**，转换工作流完全缺失（P1#6）和设置面板为空（P1#7）是最大的功能设计缺口；Liquid Glass 依赖未发布 API（P1#12）是最高的平台风险。
- **规格质量评估**：在已有的设计内容中，措辞精确、边界清晰、中文术语审慎、歧义处理得当（例如将性能目标标记为假设、将解压阈值标记为待实测调优）。问题不在于已写出的内容，而在于未写出的内容。

### 评价
规格在其 0.9 版本状态下是**诚实的**——明确标记了未关闭事项、假设和环境依赖。但它**不完整到足以安全地进入实施计划**。P0 问题如果不在设计阶段解决，将在实施中要么被忽略（导致漏洞），要么由实施者自行决定（导致后续不可修复的兼容性问题）。鉴于用户已授权后续不逐阶段审批，Codex 在推进前必须自行验证这些 P0 修订是否被合理解决。

### 修订
计划生成 5 项 P0、8 项 P1、8 项 P2 修订建议，每项附带受影响需求 ID、当前规格文本引用、攻击/失败演示和建议的具体修订方向。修订方向中明确区分了**证据**（源自输入文件的观察）、**推理**（从现有设计推演的风险）、**建议**（具体的修订措施）和**不确定性**（需要额外信息才能确定的判断）。

### 不确定性
- **P0#1、P0#2 的精确比例阈值**：建议值（提取 100:1、预览 50:1）基于业界常见实践，但需要在目标 Mac 上用真实压缩包验证，避免误伤正常的高压缩率文件（如预压缩的 PNG 或已压缩的 tarball）。
- **P0#3 的 7zz 输出契约稳定性**：需要查 7-Zip 上游文档，确认 `l -slt` 输出格式的版本间兼容性承诺。
- **P0#4 的 RARLAB 代码签名**：需要查 RARLAB 是否为 macOS 二进制签名。
- **P1#12 的 Liquid Glass 风险**：如果 Apple 在下一个 macOS 主要版本中不发布或重大变更 Liquid Glass API，部分视觉设计需要重新评估。目前无法获取关于 Liquid Glass 的权威信息。
- **Windows W0 bit-11 互操作性**：所有 Windows 物理测试环境均未建立。规格正确地将此标记为未关闭事项。但在声称 W0 认证前，至少需要一次本地 macOS → Windows 11 24H2 文件传输烟雾测试。
