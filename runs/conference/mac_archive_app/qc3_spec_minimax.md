## 规格覆盖结论

### 总体判定:不通过（不达标），需修订
v0.9 规格在**架构、领域模型、事务、安全、能力注册表、错误分类、Windows 合同、视觉方向、QC 路由**上是一份成熟度高、抽象层干净的工程文档；但在**中文术语内一致性、用户工作流的可操作细节、设置面板的逐项规则、键盘可达性、辅助功能语义、若干验收场景的端到端定义、性能预算的可验证性、错误恢复的多分支路径、跨能力组合（编辑 + 多语言 + 分卷）**上仍存在**多处必须修订的空白与冲突**。

按"用户已授权无需逐阶段审批"不构成降低标准的理由。本 QC-3 在 QC-2 已识别的 12 项缺口之外，新增/独立发现 47 项可执行修订（见 §8），其中：
- **阻断（必须改才能进入实施）**: 11 项
- **高（强烈建议在实施前关闭）**: 19 项
- **中（实施过程收敛）**: 12 项
- **润色（可后续 polish）**: 5 项

### 优势（值得保留）
- 能力注册表 + 确定性路由 + 单引擎不切换 的三件套是行业最佳实践
- 暂存/原子替换/源 SHA-256 复核的保存事务语义完整
- 错误分类表覆盖了 16 类典型失败，且与验收场景对齐
- 接收方语言（不暴露 W0/W1/W2）符合用户表达意图
- "不静默修复"原则贯穿全文，与 BetterZip/Bandizip 反例对比鲜明
- 视觉决策把"内容优先 + Finder 熟悉感 + 透明对比度降级"作为硬约束

### 关键风险（重点提示）
- 中文术语基线表与正文/菜单的术语使用**存在 6 处内部矛盾**
- 22 个核心工作流只有"成功路径"或"原则性"定义，**多分支、失败回退、跨能力组合**多为口号
- 16 个验收场景中至少 4 个（场景 5/8/12/13）**没有可被独立验证的判据**
- 性能预算的"待基准验证"贯穿全文，**没有一个数字是承诺值**
- Windows 合同对 `COM¹`/`LPT¹` 等上标设备名采用排除策略，**但未说明如何判定/呈现**
- 媒体阈值 70%/4 项被自我标记为"待实测调优"，**会导致用户视角的体验不稳定**
- "在 200% 缩放下不截断"是验收，**但没有任何布局策略**
- 16 验收场景中**没有覆盖 VoiceOver 全链路 + 暗色 + 透明降级 + 媒体视图的交叉矩阵**

### 视图切换 (§4.4)

**问题 1**: 工具栏"系统图标式分段控件"——SwiftUI 的 `Picker.pickerStyle(.segmented)` 加上 system image 是标准做法，但**当用户用 4 个以上图标时该控件会拥挤**。建议明确：当前固定 3 个图标。

**问题 2**: "用户手动选定视图后，不再自动切换"——这是关键承诺，**但 5.2.1 搜索结果视图、5.2.2 常用位置、5.3/5.4 面板是否共享这个"选定状态"**没说。规格应明确：视图状态只与"当前压缩包+当前目录"绑定。

**问题 3**: "选择按压缩包/目录在本地记忆"——**目录粒度需要权衡**：太细会爆炸，太粗会过度。建议：记忆粒度 = "压缩包 + 顶层目录哈希"。规格未说明。

**问题 4**: "列表/图标/网格"——`图标视图` 提到但 §4.4 写"图标视图（后续可启用）"——**当前 v1 范围里没图标视图**？与 §4.4 控件列出"图标视图"矛盾。规格应明确 v1 不显示"图标视图"或显示但禁用。

### Finder-like 列表 + 媒体预览自适应

**问题 5**: 媒体阈值"70% 且至少 4 个"——**这个数字没说明统计单位**：
- 是当前目录的"非文件夹"行 vs 全树？
- 是按文件数还是按总大小？
- "可安全预览"指支持快速解码还是仅非加密非特殊文件？

**问题 6**: "可建议该视图"——"建议"是横幅、模态还是浮窗？规格没定。

**问题 7**: "应用可以建议该视图"——**未来变更（例如添加"图标视图"）会改变"非文件夹项目至少 70%"的定义**——规格应给"媒体视图建议"一个不依赖列表定义的稳定语义。

**问题 8**: §4.3 "图片/视频"——**PDF、纯文本、代码片段**算不算"可安全预览的媒体"？规格没说明。Bandizip 文档明确"图片/文档/音乐"三档预览，规格未跟进。

**问题 9**: §4.3 写"底部显示附近媒体项目条带"——"附近"是什么范围？当前目录？同级？所有可见？规格没定。

**问题 10**: 媒体视图与"全树搜索"如何交互？搜索时进入媒体视图会变成什么？没说明。

**问题 11**: 媒体视图的"多选"——是条带多选 vs 主预览多选？规格仅写"键盘、触控板、滚轮与多选"——**"多选"含义未明**。

### 导航稳定性

**问题 12**: §4.1 写"切换视图不得丢失选择、滚动位置、编辑暂存状态或搜索条件"——**编辑暂存状态**和**搜索条件**在视图切换时是否应保留？强烈建议保留（"暂存不丢"是 macOS HIG 基础），但**搜索条件**在切换视图时通常要清除——规格没说。

**问题 13**: §5.2 写"返回/前进、路径上下文、搜索、视图切换和主要操作位置稳定"——**"位置稳定"**指位置不变？还指焦点保留？规格只说"位置"。

**问题 14**: §4.1 "路径栏使用可交互面包屑；每一级可跳转，也只在目标能力允许时作为安全拖放目标"——"目标能力允许"指什么？仅 ZIP/7z 可拖入创建？TAR 不能拖入？规格没说。推测应该是"按当前目录的内容可拖入到哪个层级作为新位置"，但需明确。

### 列设置 (§4.2)

**问题 15**: "用户可以调整列宽、排序、显示/隐藏列；配置按本地视图状态保存"——"本地视图状态"是按压缩包、按目录、还是按全局？规格没定。**强建议**: 按压缩包 + 顶层目录键保存，否则用户每次都重设。

**问题 16**: "默认列：名称、大小、压缩后大小、类型、修改日期"——**5 列**在 1280px 宽度上会挤。规格应给"窄宽度"折叠规则。

### 侧边栏 (§5.2)

**问题 17**: "左侧分组：最近使用、收藏位置、操作记录"——**3 个分组并列**，主目录树在"主要内容区域的源列表或首列"——**主目录树到底在侧边栏还是在主内容区**？规格写得不一致。

**问题 18**: "当前压缩包目录树位于主要内容区域的源列表或首列"——"或"字是关键；**两种可能都允许**。规格应给一个明确选择：放在侧边栏 vs 放在主区域首列。

### 状态栏 (§5.2 底部)

**问题 19**: "底部状态：选择数量、总大小、完整性或暂存编辑状态"——**只显示选择数量 vs 总大小**？macOS Finder 习惯是"X 项已选，共 Y"或"X 项"。规格未给模板。

**问题 20**: §5.2 副信息"格式、加密状态、项目数量、只读/可编辑状态"——**"只读/可编辑状态"是图标、文字、还是颜色**？规格应给视觉规范。

### 键盘可达性

**问题 21**: §6.1 写"所有快捷键需检查与系统菜单冲突，并在实现阶段用真实菜单验证"——**这是验收项但不是设计项**。应在规格里先列出已知冲突候选（例如 `⌘⇧A` 在 Xcode 是"添加到目标"）。

**问题 22**: §6.1 写"`Return` 重命名"——**与 macOS Finder 的 `Return` 行为一致**（第一次 Return 进入编辑，第二次确认）——OK 但规格没明说"按一次进入，再按一次确认"。

**问题 23**: §6.1 缺"箭头键导航"、"Tab 在工具栏与内容间切换"、"Space 预览"的明确行为描述。**强烈建议补一段"键盘导航模型"**。

### 错误/无障碍可达性

**问题 24**: §24 "所有图标按钮有简体中文可访问性标签与提示"——**"提示"是 accessibility hint 还是 tooltip**？spec 没说。`accessibilityHint` 应在交互前有意义的图标按钮上提供（"双击以解压缩选中项"），不是所有按钮。

**问题 25**: §24 "200% 文本/显示缩放与长繁体/英文字符串不能截断核心操作"——**没说布局策略**。建议加：在 Dynamic Type 最大档下，工具栏改为图标+文字双行，关键按钮"创建归档"等仍可见。

**问题 26**: §24 "完整键盘操作覆盖打开、导航、选择、预览、添加/移除/重命名、解压缩、保存和取消"——**缺"搜索、排序、视图切换、设置、帮助"**。规格应扩到"所有可达操作"。

**问题 27**: §24 "支持降低透明度、增强对比度、减少动态效果和系统强调色"——"系统强调色"对应 `NSColor.controlAccentColor`——规格应明确"工具栏选中态/列表选中条使用系统强调色，不用自定义蓝"。

### 进度与并发

**问题 28**: §9.4 写"调度器支持顺序任务、每压缩包修改互斥、最多两个外部任务及系统资源感知"——**用户视角的进度展示没说**。"操作记录"承担这个职责，但**每个操作的进度/取消/重试 UI 没说**。

**问题 29**: §5.2 底部状态"完整性或暂存编辑状态"——**当一个 1 GiB 解压正在 50% 进行时，进度条出现在哪**？规格没说。

**问题 30**: §9.4 写"红acted 诊断信息"——**"红acted"是英文**。规格正文应用"脱敏"或"已脱敏"。
