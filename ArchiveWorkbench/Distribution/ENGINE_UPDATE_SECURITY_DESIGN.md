# 项7 安全设计：app 内更新外部引擎（7zz / RARLAB rar）评估

> 状态：设计稿（待用户决策）。当前实现为"诚实版"：内置引擎随应用更新、外部引擎一键前往官网。本文给出若确需 app 内更新外部引擎时的安全方案与结论建议。

## 1. 背景与现状

- 用户需求："设置中的 4 个引擎要能单独检测更新，有更新后能直接在 app 中点击'更新引擎'后进行实际更新。"
- 现状（v1.0.9+）：`ProviderStatusView` 对内置引擎（minizip-ng / libarchive / 内嵌 7zz）标"随应用更新"；对外部引擎（7zz / RARLAB rar）标当前检测版本 + "前往官网"一键链接。**app 不联网下载、不写任何可执行文件。**

## 2. 为什么不能直接实现"app 内下载替换外部引擎"

| 风险 | 说明 |
|---|---|
| 供应链攻击 | app 联网下载二进制并替换磁盘可执行文件 = 经典中间人投毒入口；下次调用即执行恶意代码 |
| 违背核心卖点 | MacUnzip 主打"零网络调用 / 隐私优先"；app 内下载外部引擎直接破坏该承诺 |
| 许可合规 | RARLAB rar 是共享软件，许可条款要求用户自行获取/安装；app 代为下载分发可能违反许可 |
| 平台信任 | macOS Gatekeeper / 公证对"运行时自下载可执行"行为敏感，易触发安全告警 |

属 **Controlled** 级安全变更，须威胁建模 + 签名校验 + 用户显式授权流程，不应在细节优化轮次擅自实现。

## 3. 若确需实现：最小安全方案（供决策参考）

仅当用户明确授权且接受卖点调整后，按以下全部条件实施：

1. **HTTPS + 证书固定**：只从固定域名（如官网）拉取，TLS 证书 pinning。
2. **签名清单**：服务端发布 Ed25519 签名的 manifest（版本号 + 二进制 SHA-256）；app 内嵌公钥验签，下载后逐字节校验哈希，任一不符即拒绝。
3. **用户显式确认**：检测到更新仅"提示"，下载与替换必须用户点击确认；替换前备份旧二进制、失败回滚。
4. **许可确认**：RARLAB rar 更新前强制重申"用户已持有效许可、自行负责"确认框。
5. **审计日志**：每次检测/下载/替换写本地脱敏日志，可导出（复用 DiagnosticsExporter）。
6. **隔离执行**：下载落临时目录（0o700）、原子替换、替换后重新做既有 `SevenZipBinaryDiscovery`/`RARBinaryDiscovery` 可信路径与权限校验，不通过即回滚。

实施成本：高（签名基础设施 + 回滚 + 合规文案 + 持续运维）。

## 4. 推荐结论

- **短期（推荐，现状）**：保持诚实版。内置引擎随应用更新（app 更新即引擎更新，无独立下载）；外部引擎前往官网。零新增攻击面。
- **可选增量（低风险）**：若需"检测更新"体验，只做**版本提示**——opt-in 拉取一个静态 JSON（仅版本号，无下载链接执行），提示后仍引导用户去官网下载。不下载/不写可执行文件，攻击面极小，可保留零下载承诺。
- **不推荐**：app 内自动下载替换外部引擎（§3 方案即使做满也违背零网络卖点且许可存疑）。

> 决策点：选"现状" / "版本提示增量" / "完整 app 内更新（§3）"。选定后我再实施。
